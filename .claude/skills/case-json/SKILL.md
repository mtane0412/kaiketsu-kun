# ケースのJSONを作る

調べた資料をもとに、このアプリのケース（`Case`）のJSONを作ります。
最終的な成果物は、`npm run validate-case` が `OK` を返すJSONファイル1つと、作業の報告です。

## 0. 始める前に決めること

依頼に次の情報が無い場合は、調べ始める前にユーザーに確認します。

- 対象（事件名・作品名と、扱う範囲。例: 「発生から1年以内の報道」「第1〜3話」）
- 使ってよい資料（Web検索してよいか、ユーザーが渡すURL・文章だけか）
- 新しく作るのか、既存のJSON（パス）に書き足すのか

## 1. 正となる定義を読む

形式はこのスキルに書き写していません。次のファイルを読んで従ってください。

| 内容 | ファイル |
|---|---|
| 型と各項目の意味 | `src/domain/types.ts` |
| 設計の判断（発言者・経由・資料・照合・仮説の使い分け） | `docs/domain-model.md` の「モデルの要点」 |
| 記入例（現在の形式の正しいデータ） | `src/domain/sample-fictional-case.ts` |
| 本文のメンションの記法 | `src/domain/mention.ts` の冒頭のコメント |
| 日時の表記 | `src/domain/time-ref.ts` の冒頭のコメント |

**`src/domain/case-schema.ts` は形式の手本にしないでください。** 古い形式のデータを読み込むための項目
（`sources`・`events`・`statedAt`・`assessment`・`subjectPersonIds`・`speaker.personId`・日時の `earliest` など）が残っています。
これらを書くと検証で誤りになります。

## 2. 資料を集める

- 資料1件（記事1本・動画1本・会見1回・書籍の1章など）を、資料（`Interview`）1件にします。
- 資料には、分かる範囲で `title`・`url`・`at`（公開・実施の日時）・`interviewerPersonId`（媒体や聴き取った人物）を入れます。
- 本文は、ページの原文から取ります。**WebFetch の結果は要約・言い換えを含むため、`transcript` や引用に使わないでください。**
  Wikipedia は MediaWiki API（`action=query&prop=extracts&explaintext=1`）、その他のページは `curl` で取得したHTMLから本文を取り出します。
- 証言を書き起こす資料には、`transcript` に本文を入れます。本文が長い場合は、証言を書き起こす段落だけでもかまいません。
  ケースはブラウザの LocalStorage（およそ5MB）に保存されるため、本文を必要以上に入れないでください。
- 媒体（新聞社・テレビ局・県警・防犯カメラ・調書など）も人物（`Person`）として登録し、`kind` で種別を区別します。

## 3. 証言を書き起こす

### 捏造しないための規則（最も重要）

- 人物を発言者とする証言は、資料に書かれていることだけから作ります。必ず `interviewId` で資料にひもづけ、
  `quote.text` に資料の本文（`transcript`）の文字列を**一字一句そのまま**入れます（要約・言い換え・表記の修正をしない）。
- 資料に書かれていない推測・解釈・補足は、発言者を `{ "kind": "user" }` とする証言にします（経由は空）。
- 証言に「信頼できる」「疑わしい」などの評価を書きません。確からしさは発言者・経由・照合から読み手が判断します。
- 資料を確認できなかった事柄（リンク切れ・有料記事・原典を探せなかったなど）は、証言にせず未了事項（`Task`）に残します。

### 発言者と経由

`docs/domain-model.md` の「伝聞の経路は、経由で持ちます」の例に従います。判断の規則は次のとおりです。

- **発言者は「述べた者」です。文中で行動した者・話題になっている者ではありません。**
  資料が、だれの発言・発表とも書かずに述べている内容（地の文）は、その資料の媒体を発言者にし、経由は空にします。
  - Wikipedia に「行員たちは刑務官に通報を頼んだ」とある → 発言者: Wikipedia、経由: []（行員の発言ではない）
  - 記事に「農協に脅迫状が届いた」とある → 発言者: その記事の媒体（農協は脅迫された側で、述べた者ではない）
- **資料が、だれかの発言・発表・結論として書いている内容は、その人物を発言者にし、経由の最後に媒体を入れます。**
  - 新聞が「警察によると〜」と報じた → 発言者: 警察、経由: [新聞]
  - Wikipedia に「捜査本部は同一犯と結論付けた」とある → 発言者: 警視庁（捜査本部）、経由: [Wikipedia]
  - 地の文の中の台詞（「男は『爆発するぞ』と叫んだ」）→ 発言者: その男、経由: [媒体]
- 主語を省いた受け身の文（「〜と判明した」「〜に目撃されていた」「〜とされた」）は、だれが述べたかを資料が書いていないため、原則として媒体の地の文とします。
  前後の文で述べた者が明示されている場合（「捜査本部が鑑定を依頼したところ、〜と判明した」）だけ、その人物を発言者にします。
  - 「近隣の住人に目撃されていた」→ 発言者: 媒体（住人が何を述べたかは書かれていない）
- 経由を空にしてよいのは、資料そのものが発言者本人の発言である場合（本人の会見・本人の著書・本人への聴取の記録）と、発言者が媒体自身である場合だけです。
  経由が空の証言は、画面では「ユーザーが発言者から直接見聞きした」ことを表すためです。
- 「AとBが認めた」 → 発言者: [A, B] の1件。別の機会にそれぞれ述べた場合は、別々の証言にします。

### 本文（content）と、本文から導く項目

- 人物・場所・日時は、本文の中にメンション `@[表示名](person:ID)`・`@[表示名](place:ID)`・`@[表示名](date:日時)` で書きます。
- `mentionedPersonIds`・`placeId`・`when` は、本文のメンションから導いた値と一致させます（導き方は `src/domain/mention.ts` の `deriveClaimLinks`）。
  - `mentionedPersonIds`: 人物のメンションのIDを、最初に現れた順に重複なく並べる（無ければ空の配列）
  - `placeId`: 最初の場所のメンションのID（無ければキーごと書かない）
  - `when`: 最初の日時のメンションの日時（無ければキーごと書かない）
- 1件の証言には、1つの時点の事柄だけを書きます。別の時点の事柄（「事件が起きた。のちに時効が成立した」）は、別々の証言に分けます。
  本文に日時のメンションを複数書くと、最初のものが証言の日時になるためです。
- 日時の書き方の例（詳しくは `src/domain/time-ref.ts`）:
  - `1968`・`1968-12`・`1968-12-10`・`1968-12-10T09:15`（分かっている精度までを書く）
  - `1968-04-25/08-22`（4月25日〜8月22日。終わりは、始まりと同じ部分を省略できる）
  - `1968-12-10T09:15/09:50`、`1968-12-10T23:30/1968-12-11T01:00`（日をまたぐ場合は省略しない）
- 長い本文には、短い見出し（`title`）を付けます。

### 時系列の並び順

- `timelineOrder` には、すべての証言を `claim:証言のID` の形で1回ずつ、述べている内容が起きた順に並べます。
- 日時を持つ証言どうしは、日時と矛盾しない順にします（区間が重なる証言どうしは、どちらが先でもかまいません）。

## 4. 照合・関係・仮説・未了事項

どれも任意です。資料に根拠がある場合だけ作ります。

- 照合（`CrossCheck`）: 2件の証言が裏付け合う・食い違う・同じ事柄を述べている場合に作ります。食い違いの発見は調査の価値が高いので、気づいたものは残します。
  理由（`reason`）には、資料で確かめたことだけを書きます。「独立した情報源である」などは、両方の資料の出どころを確かめた場合にだけ書きます（同じ通信社の配信や、互いを引用した記事は独立ではありません）。
  出どころを確かめられなかった場合は、理由に「独立した取材に基づくかは確認できていない」と書き、確かめる作業を未了事項に残します。
- 関係（`Relationship`）: 根拠の証言を `basisClaimIds` に入れます。
- 仮説（`Hypothesis`）: ユーザーに頼まれた場合だけ作ります（見立てはユーザーのものだからです）。
- 未了事項（`Task`）: 確認しきれなかったこと・次に調べるべきことを残します。

## 5. 書き出して検証する

- ID は、記入例のように意味の分かる英小文字とハイフンの文字列にします（例: `person-neighbor`・`claim-neighbor-saw-light`）。ケース内で重複させないでください。
- 場所の座標（`latitude`・`longitude`）は、確かな場合だけ入れます。推測で入れないでください。
- 値の無い任意項目は、キーごと書きません（`null` や空文字列も書きません）。読み込みの前後で形が変わり、検証で誤りになります。
  一方、`interviews`・`crossChecks`・`relationships`・`hypotheses`・`tasks`・`personLaneOrder` などの一覧は、空でも `[]` と書きます。
- 保存先は `src/domain/private/<ケースの名前>.json` です。このディレクトリは `.gitignore` で除外されています。
  **このリポジトリは公開リポジトリです。実在の人物に関するデータを、ほかの場所に置いたりコミットしたりしないでください。**
- 書き出したら、次のコマンドで検証します。`OK` になるまで直して再実行します。

```bash
npm run validate-case -- src/domain/private/<ケースの名前>.json
```

検証の内容は `src/lib/case-file-validation.ts` の冒頭のコメントのとおりです（アプリが読み込めること・古い形式でないこと・本文と導出項目の一致・並び順・引用が本文に含まれること）。
検証が通っても、証言が資料を正しく写しているかは保証されません。3の規則を守ってください。

## 6. 報告する

ユーザーには次のことを報告します。

- JSONファイルのパスと、検証の要約（件数）
- 読み込み方（トップページの「JSONを読み込む」）
- 確認できなかったこと・判断に迷ったこと（発言者・経由の判断が分かれる証言など）と、未了事項に残した内容

報告の前に、すべての証言について「発言者は述べた者か」「経由が空の証言は、本当に本人から直接見聞きしたものか」を見直してください。
