# ドメインモデル設計メモ（検証用ドラフト）

## このリポジトリの目的

このリポジトリは、誰が何を述べたかを起点に、人物・場所を時系列で整理する調査ボードを作ります。
対象は、未解決事件の調査整理と、登場人物が膨大な作品（名探偵コナンなど）の人間関係整理の両方です。

前身は人物相関図アプリ `relationship-chart` です。前身は人物と関係を一次データとしていましたが、
このリポジトリは「証言（Claim）」を一次データとし、グラフ・時系列・証言者別・地図を派生ビューとします。

## 現在の段階

現在は、検証用の薄いUIに実データを入力して、ドメインモデルが破綻しないかを確かめる段階です。

- 型定義: `src/domain/types.ts`
- 架空の案件による記入例: `src/domain/sample-fictional-case.ts`（画面の「架空のサンプルを読み込む」で読み込めます）
- 起動: `npm run dev`
- 品質チェック: `npm run lint && npm run type-check && npm test`

UIは次の範囲に絞っています。

- 時系列のボード（ホワイトボード）: 主画面です。証言を、ユーザーが決めた並び順（相対関係）で並べます。項目はドラッグで前後に動かせます。入力専用の画面は無く、ボード上の書き足したい位置に入力欄を開きます（下記「ボードへの書き足し」）
- 証言者別ビュー: 発言者ごとに証言を一覧し、ユーザーの推測を区別して表示
- 登録済みの一覧: 人物・場所・証言の編集と削除。ボード上のメンション、または「登録済みの一覧」ボタンから、画面の右側のパネルに開きます
- 保存: ブラウザのLocalStorageへの自動保存と、JSONの書き出し・読み込み

この段階では、次のものを意図的に作っていません。

- スキーマのマイグレーション。モデルを変更したときは、書き出したJSONを変換して読み込み直します。
  保存済みデータが検証に失敗した場合、アプリはデータをLocalStorageのキー `testimony-board-case-backup` に退避します。
- 関係（`Relationship`）の入力、グラフ表示、地図、AI抽出、LLMによるエンティティの解説。

検証の手順は次の通りです。

1. ユーザーが調査中の実在の事件1件と、コナンのエピソード群1つを選びます。
2. 手元の資料から、証言を20〜30件ずつ画面で入力します。
3. 入力できなかった事柄や、ビューで不便だった点を、下記「未決事項」に追記します。
4. こまめに「JSONを書き出す」でデータを保存します。

注意: このリポジトリは公開リポジトリです。実在の人物に関する推測を含むデータはコミットしないでください。
書き出したJSONをリポジトリ内に置く場合は `src/domain/private/` に置いてください。このディレクトリは `.gitignore` で除外済みです。

## モデルの要点

| 型 | 役割 |
|---|---|
| `Case` | 1つの事件または作品。すべてのデータの入れ物。時系列ボードの並び順（`timelineOrder`）も保持 |
| `Claim` | 誰が・誰を経由して・何を述べたか。人物の発言と、ユーザーの推測の総称 |
| `Person` / `Place` | 登場する人物と場所。`Person` は、組織・記録装置・媒体（新聞、書籍、調書）を含む、発言しうる主体全般を表す。どちらにも画像を登録できる（`imageDataUrl`。登録時に長辺256px以内のJPEGへ縮小した data URL で、`src/lib/image-utils.ts` が縮小する） |
| `Relationship` | 証言から導いた結論。`basisClaimIds` で根拠を参照 |
| `TimeRef` | 曖昧さを許す時刻。原文表記と、区間または並び順を保持 |

設計判断は次のとおりです。

- **人物の発言とユーザーの推測は同じ型です。** `Claim.speaker` が `person` / `user` のどちらかで区別します。発言者を選ばない証言が、ユーザーの推測です。
- **人物は、発言しうる主体の全般を表します。** 個人だけでなく、組織（警察など）・記録装置（防犯カメラなど）・媒体（新聞、書籍、調書など）も `Person` として登録し、入力欄の「発言者」で選べます。個人・組織・記録装置・媒体を区別する項目は持ちません。名前で区別がつき、区別によって動作が変わる処理が無いためです。補足やURLは `Person.note` に書きます。記録装置の記録は確度が高い傾向にありますが、証言に真偽の評価を付けない方針のとおり、特別な表示はしません。
- **ソースという種類は持ちません。** 以前の版は、証言の出どころとなる資料を `Source` という別の種類で持ち、証言は「発言者」と「ソース」の2段で出どころを表していました。しかし「新聞が報じた」も「警察が発表した」も同じ「誰かがそう述べた」であり、ソースは「伝聞の連鎖の最後の語り手」にすぎません。そのため、媒体を人物に統合しました。報道の地の文や漫画のナレーションは、その媒体の発言です。書誌情報（種類・URL・公開時点）の項目は、詳しすぎるため持ちません。必要な場合は人物のメモ欄に書きます。
- **伝聞の経路は、経由で持ちます。** `Claim.viaPersonIds` は、発言者の発言をユーザーに伝えた人物を、伝えた順に並べた一覧です。最後の要素が、ユーザーが直接見聞きした相手です。発言者から直接見聞きした場合と、ユーザーの推測では、空です。
  - 「防犯カメラに映っていたと県警が発表したと新聞が報じた」→ 発言者: 防犯カメラ、経由: 県警 → 新聞
  - 「Aが自供したと警察の調書にある」→ 発言者: A、経由: 警察の調書。自白の強要がありうるように、「Aがそう述べた」ことと「Aがそう述べたと警察が述べている」ことは別です。
  - 「警察によるとAとBが喧嘩した。AもBも認めている」を新聞で読んだ場合 → 「喧嘩があった」は 発言者: 警察、経由: 新聞。「認めた」は 発言者: A、B、経由: 警察 → 新聞。
  - 経由を平らに並べず順序で持つのは、複数の証言が独立した裏付けなのか、同じ経路から出た1つの情報なのかを判断するためです。上の例でA・B・警察を並列の発言者にすると、実際には警察の1系統の情報が、3者による独立した裏付けに見えてしまいます。
  - 経由を持てるのは、発言者がいる証言だけです（`findCaseViolations`）。証言者別ビューは発言者でまとめ、経由した人物のグループには入れません。
  - 証言同士の入れ子（`reportedClaimId` など）にしないのは、入力が重くなるためです。経由の各段が「いつ述べたか」を個別に持つ必要が出た場合に再検討します。
- **人物の発言者は複数持てます。** 複数人が同じことを述べたと伝えられている場合は、全員を `speaker.personIds` に持つ1件の証言にします。別の経路や別の時点でそれぞれが同じことを述べた場合は、別々の証言にします。述べられた時点（`statedAt`）と経由（`viaPersonIds`）が異なり、独立した裏付けかどうかが確からしさの判断材料になるためです。発言者を1人しか持てなかった頃のデータ（`speaker.personId`）は、読み込み時に `personIds` へ変換します（`parseCase`）。
- **ソースを持っていた頃のデータは、読み込み時に変換します**（`parseCase` が呼び出す `migrateLegacySources`）。ソースは同じIDの人物に変換し、URL・公開時点・メモは人物のメモにまとめます。同じ名前の人物が登録済みの場合は、その人物へまとめます。人物の証言のソースは経由に移し、「ソース自体の記述」はソースだった人物の発言にします。本文の末尾の「@ソース」は、ソースを指定するための書き方だったため取り除き、それ以外の「@ソース」は人物のメンションに変換します。証言ごとの資料内の位置（`Claim.locator`）は、入力欄を廃止しましたが、値は保持してカードに表示します。
- **出来事を表す型はありません。** このアプリは、事件に関わる人たちの証言を決めつけずに並べて、真実に迫ろうとするものです。未解決事件では、警察発表の時系列も含めて、語られる出来事はすべて誰かの証言です。違いは、複数の人が同じことを述べているか、物的証拠があるかによる確からしさだけです。そのため「出来事」という種類は持たず、すべてを証言として時系列に並べます。ユーザーの見立ても、発言者が `user` の証言として他の証言と同列に記述します。
  - 以前の版は、同じ事柄についての証言を束ねるラベルとして出来事（`Event`）を持ち、束ねた証言同士の食い違いを表示していました。比較のたびに出来事を作って束ねる操作が重く、モデルも複雑になるため廃止しました。出来事を持っていた頃のデータは、読み込み時に束を解いて変換します（`src/domain/legacy-events.ts`）。束の位置に、束ねていた証言を当時の束の中の表示順で並べ、本文の末尾の「@出来事」は取り除き、文中の「@出来事」はタイトルの文字に戻します。出来事のメモと、証言を1件も束ねていない出来事は引き継ぎません。
- **時系列の骨格は証言です。** 時系列ビューには、すべての証言が1本の並びとして並びます。
- **時系列の位置は相対関係で持ちます。** ボード上の位置は、日時ではなく、案件が持つ並び順（`Case.timelineOrder`）で決まります。要素は `claim:証言のID` の形のキーです（接頭辞は、出来事の束もボードの項目だった頃の名残です）。日時（`Claim.when`）は任意の付加情報です。資料の多くは「Aの後、Bの前」という相対関係しか述べず、日時が分かる項目と分からない項目を1本の並びに置けないと、時系列を組み立てられないためです。実装は `src/domain/timeline-order.ts` です。
  - 並び順に載っていない証言は、末尾に登録順で並べます。削除された証言のキーは無視します。
  - **日時と矛盾する順には並べられません。** 矛盾とは、前にある項目の日時の区間が、後ろにある項目の区間より完全に後であることです。区間が重なる項目同士は、どちらの順でも矛盾としません。日時を持たない項目は、どこにでも置けます。
  - ドラッグでは、日時を持つ項目は矛盾しない範囲にだけ動かせます。動かしても日時は書き換えません。
  - 日時の入力で現在の位置が矛盾した項目は、保存時に、最も近い矛盾しない位置へ自動で動かします（`settleTimelineItems`）。日時の入力を拒否しないのは、「日時と矛盾するので動かせず、位置と矛盾するので日時を直せない」という行き詰まりを避けるためです。
  - 並び順を持たない頃に保存したデータは、読み込み時に、当時の表示順（日時の早い順）を並び順として補います（`parseCase`、`legacyTimelineOrder`）。
- **証言は、任意で見出しを持ちます。** `Claim.title` は、本文（`Claim.content`）を要約する短い文です（例: 見出し「Zによる恐喝事件があった」、本文にその詳細）。見出しのある証言は、カードに見出しを表示して本文を折りたたみ、ドラッグのつまみの名前と「登録済みの一覧」にも見出しを使います。見出しも証言の一部であり、その発言者が述べた内容の要約です。
- **時間軸は2本です。** 証言が述べる内容の時点（`Claim.when`）と、証言が述べられた時点（`Claim.statedAt`）を分けます。
- **証言に真偽の評価を付けません。** 「信頼できる」「疑わしい」「未検証」のような評価の項目は持ちません。警察の発表であっても、内容が真実であるとは限らないためです。確からしさは、誰が述べたか（`Claim.speaker`）、誰を経由して伝わったか（`Claim.viaPersonIds`）、並んだ他の証言と食い違うかから、読み手が判断します。評価を廃止する前に保存したデータの `assessment` は、読み込み時に取り除きます（`parseCase`）。
- **証言同士の食い違いは判定しません。** 食い違いは、時系列に並んだ証言を読み手が見比べて見つけます。どの証言が正しいかという基準は置きません。「同じ事柄についての証言」を機械的に比べる仕組みが必要になった場合は、証言同士を直接つなぐ形を検討します（未決事項4）。
- **曖昧な時刻は区間で持ちます。** 「1995年7月頃」は `earliest` と `latest` の区間にします。`order` は、述べられた時点（`statedAt`）を、実在の日時なしで並べるための数値です。時系列ボードの位置には使用しません。

## ボードへの書き足し

入力は、ボードへの書き足しの1種類だけです。ユーザーは、エンティティの種類ごとのフォームを選ばずに、ボード上の位置を選んで1欄に書きます。入力欄は、SNSに投稿する感覚で書けるよう、任意の見出し・本文の1欄と、投稿ボタンの横の「発言者」だけを表示します。書いたものは常に証言（`Claim`）として保存し、人物・場所は本文の「@」から抽出します。誰の発言か、誰を経由して伝わったかは本文には書かず、「発言者」で選びます（将来はLLMによる抽出を、この1欄の後段に加える構想です）。

書いた位置は、次の規則で証言の初期値になります。実装は `src/components/views/TimelineView.tsx` と `src/components/views/BoardComposer.tsx` です。

| 書いた位置 | 証言の初期値 |
|---|---|
| 時系列の項目の前 | 日時は付けず、並び順のその位置に並べます |
| 「ボードに書き足す」 | 並び順の末尾に並べます |

- 差し込み口は、すべての項目の前に表示します。位置を日時ではなく並び順で持つため、前後の項目の日時の有無に関係なく書き足せます。
- 項目は、左端のつまみをドラッグして前後に動かします（`@dnd-kit`）。キーボードでは、つまみの上でスペースキー、上下の矢印キー、スペースキーの順に操作します。ドラッグ中は、日時と矛盾するため置けない位置の項目を薄く表示します。
- ボード上の証言は「編集」でその場の入力欄に切り替わり、同じ入力欄から削除できます。その場の編集で変更できるのは本文・発言者・経由で、入力済みの日時は保持します。
- 日時は、証言の「詳細」から、画面の右側のパネルのフォームで編集します。本文から日時を読み取る処理は、LLMによる抽出の段階で加える構想です。
- Ctrl+Enter（macOSではCommand+Enter）で保存します。

## 証言の入力とメンション

証言の本文は、ホワイトボードに書くのと同じ順序で書き進められることを目標にしています。
ユーザーは先に人物や場所を台帳に登録する必要がなく、本文を書きながら「@」でエンティティ（人物・場所の総称）を参照し、未登録の名前はその場で新規作成します。

実装は `src/domain/mention.ts`（解析と導出）と `src/components/forms/MentionTextarea.tsx`（入力欄）です。

- **本文の形式。** `Claim.content` は、参照を `@[表示名](種類:ID)` の形式のトークンとして含みます。種類は `person` / `place` です。表示名は控えであり、画面はIDから引いた現在の名前を表示します。
- **導出の規則。** `Claim` の `placeId`・`mentionedPersonIds` は、フォームが保存時に本文から導出します。
  - 場所は、最初のメンションを採用します。人物のメンションは、言及している人物です。
- **発言者と経由の選択。** 発言者（`Claim.speaker`）と経由（`Claim.viaPersonIds`）は本文から導出せず、投稿ボタンの横の「発言者」で選びます（`src/components/forms/SpeakerPicker.tsx`）。ボードへの書き足し・その場の編集・右側のパネルのフォームのすべてで選べます。
  - パネルには「発言者」と「経由」の2つの欄があり、それぞれ登録済みの人物を複数選べます。経由は、選んだ順が伝えた順になります。
  - 発言者を誰も選ばない証言は、ユーザーの推測です。発言者を選ばずに経由だけを選んだ証言は保存できません。
  - どちらの欄でも、未登録の人物や媒体を「人物を追加」から名前だけで新規作成でき、証言と同時に保存します。
  - ボタンは「発言者: 隣家の住人（架空日報 朝刊 による）」のように現在の選択を示します。カードも同じ形で示します。
  - パネルは、開く時点でボタンの上下のうち空きが広い側に開きます（ボード上の入力欄は画面の下端にも上端にも開くためです）。
  - 以前の版では、本文の先頭を「@人物:」と書くとその人物を発言者として導出していました。書き方で発言者が決まることが分かりにくいため廃止しました。その頃に保存した本文に残っている発言者の記法は、読み込み時に取り除きます（`parseCase` が呼び出す `stripLegacySpeakerPrefix`）。発言者は `speaker` に保存済みのため、情報は失われません。
- **キーボード操作。** 候補の先頭が登録済みのエンティティの場合は、Enterキーだけで確定します。新規作成の選択肢しか無い場合は、矢印キーで選ぶまでEnterキーは改行として働きます（メールアドレスの「@」などで意図しないエンティティを作らないためです）。
- **入力欄での表示と削除。** 確定したメンションは、入力欄の中で種類ごとの背景色（ボードのメンションと同じ色）をつけて示します。未確定の「@」には色をつけません。確定したメンションの直後または途中でBackspaceキーを押すと、1文字ずつではなくメンション全体を削除し、下書きの登録からも外します。入力欄は `textarea` のままとし、同じ文字組みの層を背面に重ねて背景色だけを描きます（`MentionTextarea`）。
- **新規作成。** 新規作成したエンティティは名前だけを持ち、証言と同じ1回の検証でまとめて保存します（`useCaseStore` の `upsertMany`）。本文からも発言者・経由からも外したエンティティは保存しません。
- **検証。** `findCaseViolations` は、本文のトークンの参照先が案件内に存在することも検証します。
- **メンション導入前のデータ。** 本文にトークンを持たない証言を編集すると、フォームは項目にだけ保存されていた参照を本文にメンションとして補います。

既知の制約は次の通りです。

- 日本語は単語を空白で区切らないため、下書きで確定済みの「山田」がある場合、「@山田花子」の候補を開けません。
- 1つの証言が複数の場所に言及する場合、`placeId` は最初の1件だけを保持します。2件目以降は本文のトークンとしてのみ残ります。
- エンティティのメモ欄と、証言の見出し（`Claim.title`）は、メンションに未対応です。見出しに「@」で書いた名前は、場所・言及している人物の導出に使いません。

## 今後の構想: LLMによるエンティティの解説

蓄積した証言をもとに、人物・場所の解説をLLMで生成する構想があります。未実装で、方針は次の通りです。

- 生成した文章は、ユーザーが書く `note` とは別の項目に、生成元の証言のIDとともに保存します。このモデルは人物の発言とユーザーの推測を構造で区別しており、AIの文章がユーザーの記述に混ざるとその区別が崩れるためです。
- このアプリは実在の人物に関する推測を扱います。端末内で完結する Gemini Nano（Chrome の組み込みAI）を既定とし、OpenRouter 経由の外部LLMは、ユーザーがAPIキーを設定して明示的に有効にした場合だけ使用します。

## 未決事項

実データの書き起こしで確かめる項目です。

1. **伝聞の扱い（経由で対応済み）。** 情報が何段も経由する連鎖は、`Claim.viaPersonIds` で表すことにしました。残る論点は、経由の各段が述べた時点を個別に持てない点と、「AがBから聞いた」のBの発言そのものを別の証言として参照できない点です。必要になった場合は、`Claim` 同士の参照（`reportedClaimId` など）を検討します。
2. **相対的な時刻。** 「事件Xの前」「17年前」は、時系列ボードの並び順（`Case.timelineOrder`）で表すことにしました。残る論点は、並び順が1本の全順序であるため、「AとBのどちらが先か分からない」という部分的な順序を表せない点です。コナンは作中の現在が固定されないため、この項目の影響が大きいと見込んでいます。
3. **特定の時点を持たない証言。** 人物評や関係についての証言（「2人は不仲だった」）を、時系列の並びの中の `Claim` と `Relationship.basisClaimIds` の組み合わせで十分に扱えるか。
4. **証言同士の関係。** 「この証言はあの証言を裏付ける／否定する」「同じ事柄について述べている」を明示的に持つか、時系列での並置だけで足りるか。以前の版の出来事（`Event`）による束ねは、操作が重いため廃止しました。
5. **関係の時間変化。** `Relationship` に有効期間を持たせるか。前身のスナップショット機能（グラフ全体の手動コピー）は引き継がず、時点を指定して導出する方針です。
6. **人物の同一性。** 偽名や変装（コナンで頻出）を `aliases` で足りるとするか、「人物Aと人物Bは同一人物である」という証言として扱うか。
