# ドメインモデル設計メモ（検証用ドラフト）

## このリポジトリの目的

このリポジトリは、証言とソースを起点に、出来事・人物・場所を時系列で整理する調査ボードを作ります。
対象は、未解決事件の調査整理と、登場人物が膨大な作品（名探偵コナンなど）の人間関係整理の両方です。

前身は人物相関図アプリ `relationship-chart` です。前身は人物と関係を一次データとしていましたが、
このリポジトリは「主張（Claim）」を一次データとし、グラフ・時系列・証言者別・地図を派生ビューとします。

## 現在の段階

現在は、検証用の薄いUIに実データを入力して、ドメインモデルが破綻しないかを確かめる段階です。

- 型定義: `src/domain/types.ts`
- 架空の案件による記入例: `src/domain/sample-fictional-case.ts`（画面の「架空のサンプルを読み込む」で読み込めます）
- 起動: `npm run dev`
- 品質チェック: `npm run lint && npm run type-check && npm test`

UIは次の範囲に絞っています。

- 時系列のボード（ホワイトボード）: 主画面です。出来事の束と、出来事に束ねていない主張を、主張が述べる日時の順に並べ、同じ出来事に束ねた主張同士の食い違いを表示します。入力専用の画面は無く、ボード上の書き足したい位置に入力欄を開きます（下記「ボードへの書き足し」）
- 証言者別ビュー: 発言者ごとに主張を一覧し、ユーザーの推測を区別して表示
- 登録済みの一覧: ソース・人物・場所・出来事・主張の編集と削除。ボード上のメンション・出来事の見出し、または「登録済みの一覧」ボタンから、画面の右側のパネルに開きます
- 保存: ブラウザのLocalStorageへの自動保存と、JSONの書き出し・読み込み

この段階では、次のものを意図的に作っていません。

- スキーマのマイグレーション。モデルを変更したときは、書き出したJSONを変換して読み込み直します。
  保存済みデータが検証に失敗した場合、アプリはデータをLocalStorageのキー `testimony-board-case-backup` に退避します。
- 関係（`Relationship`）の入力、グラフ表示、地図、AI抽出、LLMによるエンティティの解説。

検証の手順は次の通りです。

1. ユーザーが調査中の実在の事件1件と、コナンのエピソード群1つを選びます。
2. 手元の資料から、主張を20〜30件ずつ画面で入力します。
3. 入力できなかった事柄や、ビューで不便だった点を、下記「未決事項」に追記します。
4. こまめに「JSONを書き出す」でデータを保存します。

注意: このリポジトリは公開リポジトリです。実在の人物に関する推測を含むデータはコミットしないでください。
書き出したJSONをリポジトリ内に置く場合は `src/domain/private/` に置いてください。このディレクトリは `.gitignore` で除外済みです。

## モデルの要点

| 型 | 役割 |
|---|---|
| `Case` | 1つの事件または作品。すべてのデータの入れ物 |
| `Source` | 主張の出どころ（記事・書籍・判決文・漫画の話数） |
| `Claim` | 誰が・どのソースで・何を述べたか。証言とユーザーの推測の総称 |
| `Event` | 同じ事柄についての主張を束ねるラベル。日時・場所・人物は束ねた主張から導出 |
| `Person` / `Place` | 登場する人物と場所。`Person` は、組織や記録装置を含む、発言しうる主体全般を表す |
| `Relationship` | 主張から導いた結論。`basisClaimIds` で根拠を参照 |
| `TimeRef` | 曖昧さを許す時刻。原文表記と、区間または並び順を保持 |

設計判断は次のとおりです。

- **証言と推測は同じ型です。** `Claim.speaker` が `person` / `source` / `user` のどれかで区別します。
- **人物は、発言しうる主体の全般を表します。** 個人だけでなく、組織（警察など）と記録装置（防犯カメラなど）も `Person` として登録し、`@県警: …` のように発言者にできます。個人・組織・記録装置を区別する項目は持ちません。名前で区別がつき、区別によって動作が変わる処理が無いためです。補足は `Person.note` に書きます。記録装置の記録は確度が高い傾向にありますが、主張に真偽の評価を付けない方針のとおり、特別な表示はしません。
  - ソースが「県警の発表によると、防犯カメラに映っていた」と伝えている場合は、発言者を県警とし、防犯カメラは本文で言及します（`@県警: @県道の防犯カメラ に…が映っていた。 @架空日報 朝刊`）。記録の内容が、誰の発表を経て届いたのかを残すためです。
  - 公開された映像そのものをソースとして内容を書き起こす場合は、記録装置を発言者にします（`@県道の防犯カメラ: … @公開された映像`）。
- **人物の発言者は複数持てます。** 1つのソースが複数人の同じ発言として伝えている場合は、全員を `speaker.personIds` に持つ1件の主張にします。別のソースや別の時点でそれぞれが同じことを述べた場合は、別々の主張にします。述べられた時点（`statedAt`）とソース（`sourceId`）が異なり、独立した裏付けかどうかが確からしさの判断材料になるためです。発言者を1人しか持てなかった頃のデータ（`speaker.personId`）は、読み込み時に `personIds` へ変換します（`parseCase`）。
- **出来事は見立てを持ちません。** 未解決事件では、警察発表の時系列も含めて、すべての出来事が誰かの主張です。違いは、複数の証言や物的証拠による確からしさだけです。ユーザーの見立てを出来事として特別に保持すると、その時点で比較が偏ります。そのため `Event` はタイトルとメモだけを持つラベルとし、ユーザーの見立ては、発言者が `user` の主張として他の主張と同列に記述します。
- **時系列の骨格は主張です。** 時系列ビュー上の位置は `Claim.when` で決まります。出来事の束の位置は、束ねた主張が述べる日時のうち最も早いものです。出来事に束ねていない主張も、`when` を持てば時系列に並びます。
- **時間軸は2本です。** 出来事が起きた時点（`Claim.when`）と、主張が述べられた時点（`Claim.statedAt`）を分けます。
- **主張に真偽の評価を付けません。** 「信頼できる」「疑わしい」「未検証」のような評価の項目は持ちません。警察の発表であっても、内容が真実であるとは限らないためです。確からしさは、誰が述べたか（`Claim.speaker`）、どのソースに拠るか（`Claim.sourceId`）、他の主張と食い違うかから、読み手が判断します。評価を廃止する前に保存したデータの `assessment` は、読み込み時に取り除きます（`parseCase`）。
- **矛盾は主張同士の比較で表れます。** 同じ出来事に束ねた主張同士で、述べる日時の区間が重ならない場合、または述べる場所が異なる場合に、食い違いとして表示します。どの主張が正しいかという基準は置きません。
- **曖昧な時刻は区間で持ちます。** 「1995年7月頃」は `earliest` と `latest` の区間にします。実在の日時が無い作中の時系列は `order` で並べます。

## ボードへの書き足し

入力は、ボードへの書き足しの1種類だけです。ユーザーは、エンティティの種類ごとのフォームを選ばずに、ボード上の位置を選んで1欄に書きます。入力欄は、SNSに投稿する感覚で書けるよう、本文の1欄と投稿ボタンだけを表示します。書いたものは常に主張（`Claim`）として保存し、人物・場所・出来事・ソースは本文の「@」から抽出します（将来はLLMによる抽出を、この1欄の後段に加える構想です）。

書いた位置は、次の規則で主張の初期値になります。実装は `src/components/views/TimelineView.tsx` と `src/components/views/BoardComposer.tsx` です。

| 書いた位置 | 主張の初期値 |
|---|---|
| 出来事の束の中 | その出来事に束ねます。本文に出来事のメンションが無い場合、保存時に出来事のメンションを本文の末尾に補います（「参照は本文から導出する」規則を保つためです） |
| 時系列の項目と項目の間 | 前後の日時から求めた区間（`timeRefBetween`、`src/domain/time-ref.ts`）を、主張が述べる日時として自動で付けます。入力欄には、付ける日時を表示するだけで、入力はさせません |
| 「ボードに書き足す」 | 初期値を持ちません。日時を入れなければ「時期不明」の枠に並びます |

- 項目と項目の間の差し込み口は、前後がどちらも日時を持つ場合、またはどちらも並び順（`order`）だけを持つ場合にだけ表示します。それ以外は間を求められないためです。
- ボード上の主張は「編集」でその場の入力欄に切り替わり、同じ入力欄から削除できます。その場の編集で変更できるのは本文だけで、入力済みの日時・ソース内の位置は保持します。
- 日時・ソース内の位置は、主張の「詳細」から、画面の右側のパネルのフォームで編集します。本文から日時を読み取る処理は、LLMによる抽出の段階で加える構想です。
- Ctrl+Enter（macOSではCommand+Enter）で保存します。

## 主張の入力とメンション

主張の本文は、ホワイトボードに書くのと同じ順序で書き進められることを目標にしています。
ユーザーは先に人物や場所を台帳に登録する必要がなく、本文を書きながら「@」でエンティティ（人物・場所・出来事・ソースの総称）を参照し、未登録の名前はその場で新規作成します。

実装は `src/domain/mention.ts`（解析と導出）と `src/components/forms/MentionTextarea.tsx`（入力欄）です。

- **本文の形式。** `Claim.content` は、参照を `@[表示名](種類:ID)` の形式のトークンとして含みます。種類は `person` / `place` / `event` / `source` です。表示名は控えであり、画面はIDから引いた現在の名前を表示します。
- **導出の規則。** `Claim` の `speaker`・`sourceId`・`eventId`・`placeId`・`mentionedPersonIds` は、フォームが保存時に本文から導出します。
  - 本文の先頭が人物のメンションで、直後がコロン（`:` または `：`）の場合、その人物が発言者です。人物のメンションを空白または読点（`、`）で区切って並べた場合（`@A @B:`）は、全員が発言者です。並びの途中に「と」などの文章を挟んだ場合は、発言者として扱いません。
  - 発言者の人物がいない場合、ソースのメンションがあれば「ソース自体の記述」、無ければ「ユーザーの推測」です。
  - ソース・出来事・場所は、それぞれ最初のメンションを採用します。発言者以外の人物のメンションは、言及している人物です。
- **キーボード操作。** 候補の先頭が登録済みのエンティティの場合は、Enterキーだけで確定します。新規作成の選択肢しか無い場合は、矢印キーで選ぶまでEnterキーは改行として働きます（メールアドレスの「@」などで意図しないエンティティを作らないためです）。
- **入力欄での表示と削除。** 確定したメンションは、入力欄の中で種類ごとの背景色（ボードのメンションと同じ色）をつけて示します。未確定の「@」には色をつけません。確定したメンションの直後または途中でBackspaceキーを押すと、1文字ずつではなくメンション全体を削除し、下書きの登録からも外します。入力欄は `textarea` のままとし、同じ文字組みの層を背面に重ねて背景色だけを描きます（`MentionTextarea`）。
- **新規作成。** 新規作成したエンティティは名前だけを持ち、主張と同じ1回の検証でまとめて保存します（`useCaseStore` の `upsertMany`）。本文から消したエンティティは保存しません。ソースの種類は「その他」で作成するため、必要に応じてソースの編集画面で変更します。
- **検証。** `findCaseViolations` は、本文のトークンの参照先が案件内に存在することも検証します。
- **メンション導入前のデータ。** 本文にトークンを持たない主張を編集すると、フォームは項目にだけ保存されていた参照を本文にメンションとして補います。

既知の制約は次の通りです。

- 日本語は単語を空白で区切らないため、下書きで確定済みの「山田」がある場合、「@山田花子」の候補を開けません。
- 1つの主張が複数の場所や出来事に言及する場合、`placeId` と `eventId` は最初の1件だけを保持します。2件目以降は本文のトークンとしてのみ残ります。
- 出来事のメモ欄（`Event.description`）と、その他のエンティティのメモ欄は、メンションに未対応です。

## 今後の構想: LLMによるエンティティの解説

蓄積した主張をもとに、人物・場所・出来事の解説をLLMで生成する構想があります。未実装で、方針は次の通りです。

- 生成した文章は、ユーザーが書く `note` とは別の項目に、生成元の主張のIDとともに保存します。このモデルは証言とユーザーの推測を構造で区別しており、AIの文章がユーザーの記述に混ざるとその区別が崩れるためです。
- このアプリは実在の人物に関する推測を扱います。端末内で完結する Gemini Nano（Chrome の組み込みAI）を既定とし、OpenRouter 経由の外部LLMは、ユーザーがAPIキーを設定して明示的に有効にした場合だけ使用します。

## 未決事項

実データの書き起こしで確かめる項目です。

1. **伝聞の扱い。** 「AがBから聞いた」という証言を、`Claim` 同士の参照（`reportedClaimId` など）で表す必要があるか。防犯カメラの記録を、県警が発表し、新聞が報じた場合のように、情報が何段も経由する連鎖も同じ問題です。現在のモデルが表せるのは「発言者」と「ソース」の2段だけのため、当面は、発言者を県警、言及を防犯カメラ、ソースを新聞として記述します。
2. **相対的な時刻。** 「事件Xの前」「17年前」を `TimeRef.order` の手動指定で足りるとするか、出来事への相対参照を持たせるか。コナンは作中の現在が固定されないため、この項目の影響が大きいと見込んでいます。
3. **出来事を伴わない主張。** 人物評や関係についての証言（「2人は不仲だった」）を、`eventId` なしの `Claim` と `Relationship.basisClaimIds` の組み合わせで十分に扱えるか。
4. **主張同士の関係。** 「この証言はあの証言を裏付ける／否定する」を明示的に持つか、同じ `eventId` を持つ主張の並置と食い違いの表示で足りるか。
5. **関係の時間変化。** `Relationship` に有効期間を持たせるか。前身のスナップショット機能（グラフ全体の手動コピー）は引き継がず、時点を指定して導出する方針です。
6. **人物の同一性。** 偽名や変装（コナンで頻出）を `aliases` で足りるとするか、「人物Aと人物Bは同一人物である」という主張として扱うか。

モデルの検証後、次の順で移植します。ビューの実装順は、時系列、グラフ、地図の順です。

- グラフ表示: `src/lib/graph-utils.ts`、ノード・エッジのコンポーネント群、`src/lib/node-intersection.ts`
