# ドメインモデル設計メモ（検証用ドラフト）

## このリポジトリの目的

このリポジトリは、証言とソースを起点に、出来事・人物・場所を時系列で整理する調査ボードを作ります。
対象は、未解決事件の調査整理と、登場人物が膨大な作品（名探偵コナンなど）の人間関係整理の両方です。

前身は人物相関図アプリ `relationship-chart` です。前身は人物と関係を一次データとしていましたが、
このリポジトリは「主張（Claim）」を一次データとし、グラフ・時系列・証言者別・地図を派生ビューとします。

## 現在の段階

現在は、検証用の薄いUIに実データを入力して、ドメインモデルが破綻しないかを確かめる段階です。

- 型定義: `src/domain/types.ts`
- 架空の案件による記入例: `src/domain/sample-fictional-case.ts`（画面の「架空のサンプルを読み込む」で読み込めます）
- 起動: `npm run dev`
- 品質チェック: `npm run lint && npm run type-check && npm test`

UIは次の範囲に絞っています。

- 入力: ソース・人物・場所・出来事・主張の登録、編集、削除。主張は本文1欄に「@」でメンションを書いて入力します（下記「主張の入力とメンション」）
- 時系列ビュー: 出来事を起きた時点の順に並べ、主張を並置し、見立てとの食い違いを表示
- 証言者別ビュー: 発言者ごとに主張を一覧し、ユーザーの推測を区別して表示
- 保存: ブラウザのLocalStorageへの自動保存と、JSONの書き出し・読み込み

この段階では、次のものを意図的に作っていません。

- スキーマのマイグレーション。モデルを変更したときは、書き出したJSONを変換して読み込み直します。
  保存済みデータが検証に失敗した場合、アプリはデータをLocalStorageのキー `testimony-board-case-backup` に退避します。
- 関係（`Relationship`）の入力、グラフ表示、地図、AI抽出、LLMによるエンティティの解説。

検証の手順は次の通りです。

1. ユーザーが調査中の実在の事件1件と、コナンのエピソード群1つを選びます。
2. 手元の資料から、主張を20〜30件ずつ画面で入力します。
3. 入力できなかった事柄や、ビューで不便だった点を、下記「未決事項」に追記します。
4. こまめに「JSONを書き出す」でデータを保存します。

注意: このリポジトリは公開リポジトリです。実在の人物に関する推測を含むデータはコミットしないでください。
書き出したJSONをリポジトリ内に置く場合は `src/domain/private/` に置いてください。このディレクトリは `.gitignore` で除外済みです。

## モデルの要点

| 型 | 役割 |
|---|---|
| `Case` | 1つの事件または作品。すべてのデータの入れ物 |
| `Source` | 主張の出どころ（記事・書籍・判決文・漫画の話数） |
| `Claim` | 誰が・どのソースで・何を述べたか。証言とユーザーの推測の総称 |
| `Event` | 起きたとされること。ユーザーが現時点で採用している見立てを保持 |
| `Person` / `Place` | 登場する人物と場所 |
| `Relationship` | 主張から導いた結論。`basisClaimIds` で根拠を参照 |
| `TimeRef` | 曖昧さを許す時刻。原文表記と、区間または並び順を保持 |

設計判断は次の4点です。

- **証言と推測は同じ型です。** `Claim.speaker` が `person` / `source` / `user` のどれかで区別します。
- **時間軸は2本です。** 出来事が起きた時点（`Event.when`、`Claim.when`）と、主張が述べられた時点（`Claim.statedAt`）を分けます。
- **矛盾は構造で表れます。** `Event` はユーザーの見立てを持ち、`Claim` は各証言が述べる日時・場所を持ちます。両者の食い違いが矛盾です。
- **曖昧な時刻は区間で持ちます。** 「1995年7月頃」は `earliest` と `latest` の区間にします。実在の日時が無い作中の時系列は `order` で並べます。

## 主張の入力とメンション

主張の入力は、ホワイトボードに書くのと同じ順序で進められることを目標にしています。
ユーザーは先に人物や場所を台帳に登録する必要がなく、本文を書きながら「@」でエンティティ（人物・場所・出来事・ソースの総称）を参照し、未登録の名前はその場で新規作成します。

実装は `src/domain/mention.ts`（解析と導出）と `src/components/forms/MentionTextarea.tsx`（入力欄）です。

- **本文の形式。** `Claim.content` は、参照を `@[表示名](種類:ID)` の形式のトークンとして含みます。種類は `person` / `place` / `event` / `source` です。表示名は控えであり、画面はIDから引いた現在の名前を表示します。
- **導出の規則。** `Claim` の `speaker`・`sourceId`・`eventId`・`placeId`・`mentionedPersonIds` は、フォームが保存時に本文から導出します。
  - 本文の先頭が人物のメンションで、直後がコロン（`:` または `：`）の場合、その人物が発言者です。
  - 発言者の人物がいない場合、ソースのメンションがあれば「ソース自体の記述」、無ければ「ユーザーの推測」です。
  - ソース・出来事・場所は、それぞれ最初のメンションを採用します。発言者以外の人物のメンションは、言及している人物です。
- **新規作成。** 新規作成したエンティティは名前だけを持ち、主張と同じ1回の検証でまとめて保存します（`useCaseStore` の `upsertMany`）。本文から消したエンティティは保存しません。ソースの種類は「その他」で作成するため、必要に応じてソースの編集画面で変更します。
- **検証。** `findCaseViolations` は、本文のトークンの参照先が案件内に存在することも検証します。
- **メンション導入前のデータ。** 本文にトークンを持たない主張を編集すると、フォームは項目にだけ保存されていた参照を本文にメンションとして補います。

既知の制約は次の通りです。

- 日本語は単語を空白で区切らないため、下書きで確定済みの「山田」がある場合、「@山田花子」の候補を開けません。
- 1つの主張が複数の場所や出来事に言及する場合、`placeId` と `eventId` は最初の1件だけを保持します。2件目以降は本文のトークンとしてのみ残ります。
- 出来事の説明欄（`Event.description`）とメモ欄は、メンションに未対応です。

## 今後の構想: LLMによるエンティティの解説

蓄積した主張をもとに、人物・場所・出来事の解説をLLMで生成する構想があります。未実装で、方針は次の通りです。

- 生成した文章は、ユーザーが書く `note` とは別の項目に、生成元の主張のIDとともに保存します。このモデルは証言とユーザーの推測を構造で区別しており、AIの文章がユーザーの記述に混ざるとその区別が崩れるためです。
- このアプリは実在の人物に関する推測を扱います。端末内で完結する Gemini Nano（Chrome の組み込みAI）を既定とし、OpenRouter 経由の外部LLMは、ユーザーがAPIキーを設定して明示的に有効にした場合だけ使用します。

## 未決事項

実データの書き起こしで確かめる項目です。

1. **伝聞の扱い。** 「AがBから聞いた」という証言を、`Claim` 同士の参照（`reportedClaimId` など）で表す必要があるか。
2. **相対的な時刻。** 「事件Xの前」「17年前」を `TimeRef.order` の手動指定で足りるとするか、出来事への相対参照を持たせるか。コナンは作中の現在が固定されないため、この項目の影響が大きいと見込んでいます。
3. **出来事を伴わない主張。** 人物評や関係についての証言（「2人は不仲だった」）を、`eventId` なしの `Claim` と `Relationship.basisClaimIds` の組み合わせで十分に扱えるか。
4. **主張同士の関係。** 「この証言はあの証言を裏付ける／否定する」を明示的に持つか、同じ `eventId` を持つ主張の並置で足りるか。
5. **関係の時間変化。** `Relationship` に有効期間を持たせるか。前身のスナップショット機能（グラフ全体の手動コピー）は引き継がず、時点を指定して導出する方針です。
6. **人物の同一性。** 偽名や変装（コナンで頻出）を `aliases` で足りるとするか、「人物Aと人物Bは同一人物である」という主張として扱うか。
